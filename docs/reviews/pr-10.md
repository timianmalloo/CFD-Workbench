# PR #10 — Fable owner review

PR #10 "W-2: qualify Ruling 145 native sharing behavior" (origin/win/store-b2-r145, reviewed head e2e47765) was
reviewed by the Fable owner on the Mac on 2026-10-08 under Ruling 106. Verdict: **APPROVE WITH CONDITIONS**, issued as
**Ruling 152**. Each finding is Verified (observed at the reviewed head) unless marked Inferred.

## Findings

1. **Red first (Ruling 145 (1)) is partly literal.** `r145-initial.stdout.txt`: the ShareRead|Delete case passed on
   its first run, and the ShareRead-only case failed with `Expected DOC-CONFLICT; actual ` (blank). The cycle-1,
   cycle-2 and head runs show `RESULT failures=0` (`ran=11 skipped=687`) on `NATIVE-ENV os=10.0.26300.0 arch=X64
   filesystem=NTFS`. Repairs are 2/2. The exit codes appear only in the markdown table (Inferred). The historical probe
   `WindowsNative_Replace_HeldReaderKeepsOldImage` is byte-identical from base to head.
2. **Class 65 is the only primitive (Ruling 145 (2)).** `WindowsNative.cs:167` `Rename` uses `RenameApi.NtRelative`.
   `SetFileInformationByHandle` is reachable only from three explicit probe entry points, and the file has no `catch`.
   The attribution probe records `WIN32-EX22-NULL-ROOT-ABSOLUTE … Win32=0` and `WIN32-CLASS3-ROOTED … Win32=87`, with
   identity and bytes preserved. So the 87 comes from the rooted Win32 form on this host, not from the Ex22 ABI. The
   `FileRenameInfo = 3` ordinal is Inferred (not checked against the SDK header).
3. **Win32 32 maps to DOC-CONFLICT (Ruling 145 (3)).** `WindowsNative.cs:260` and design §4 (lines 182–190) agree:
   never DOC-IO, no automatic retry, no production admission. Caveat: the `else` branch labels every other Win32 error
   DOC-IO (for example 183 or 5), and nothing qualifies that. See condition 4.
4. **Fail-closed (Ruling 145 (4)).** No diff touches ProjectStore, Desktop, the CLI or SectionLibrary.
   `WindowsStore_Unqualified_ProductionAdmissionRemainsClosed` passes.
5. **Privacy (Ruling 145 (5)).** The PROOF-PII scan over the 15 head files finds 0 hits. `r145-check-docs.stderr.txt`
   has a `C:/Projects/...` checkout path with no user name.
6. **Lease.** All changes are in-lease. The diff has no overlap with the Mac WSF track (`UserFile` readers with
   `FileShare.Read | FileShare.Delete`), and the two are consistent: case (i) is the reader shape WSF adopts.
7. **C# quality.** Every declaration uses `[LibraryImport]` with `DefaultDllImportSearchPaths(System32)`.
   `SafeFileHandle` AddRef/Release sits in `try/finally`. Failures throw `NativeFailure` with the last P/Invoke error,
   and NTSTATUS is captured before `RtlNtStatusToDosError`. Nits, with no condition attached:
   - `ProbeWin32AbsoluteRename` AddRefs a parent handle it never uses.
   - The absolute-path guard is ad hoc but limited to the fixture.
8. **Labels.** Case (i) is labelled "CHARACTERIZATION GREEN", and "production admission remains false". No label
   claims more than its evidence.
9. **PR #12 dependency.** The full-ring result at 9eef0489 appears in #10 only as a PR comment and an xmsg line. Its raw
   logs are in PR #12. None of #10's own claims depends on it.

## Rulings (Ruling 152)

- **Red-first disposition accepted.** Case (i) characterizes behaviour that PR #8 already built. Its power to tell
  good from bad shows in case (ii) (same primitive, deterministic refusal) and in the unchanged historical probe, which
  still fails with Win32 32. Case (ii)'s red is genuine. No regression is manufactured to make a red.
- **Historical probe.** Its body stays byte-unchanged. The Windows ring may list it in a known-expected-failure manifest
  keyed to Ruling 145, so the ring's exit reflects only unexpected failures. The Mac owns that mechanism (tools/).

## Conditions

1. **Pre-merge (PC, docs only):** in `r145-qualification.md` proof-pack row 1, replace "Owner red-first disposition
   required" with the disposition above, citing this review.
2. **Pre-merge (Mac, at the join):** `python3 tools/check-docs.py` green at the merge head.
3. **Follow-up (Mac):** a known-expected-failure manifest for the Windows ring, keyed to rulings.
4. **Follow-up (PC, before any adapter reads `ProductCode`):** `ProductCode` returns DOC-CONFLICT for Win32 32 and no
   code otherwise. Design §4 says so, and a test asserts the unmapped branch (for example Win32 183). A full Win32-to-DOC
   table instead needs a data-persistence-architect review.

Nothing goes to the operator. The remaining Windows ring failures belong to the WFX2 receipt (PR #12).
