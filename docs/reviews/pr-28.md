## Nice reconciliation

- The case YAML stays byte-identical.
  - `nice: 10` is the increment the adapter requests (`of-command-l3.sh:26` runs `nice -n 10`), and the unit is
    `Nice=10`.
  - Rewriting it would rewrite a past record and break the `l3-prepared.json` hash binding.
- **NI 19 is an observed fact, not a correction.**
  - `nice(1)` increments relative to the caller, and Linux clamps at 19, so 10 + 10 gives 19. That mechanism is Verified
    as Linux semantics.
  - For this run it is Inferred, because the mpirun parent (PID 1113) was not enumerated.
- **The record lives in the proof folder, not `cases/`.** One run has one case file. `actual-launch.json` is
  manifest-bound and never edited. One row is one observation of one run's launch parameters at one capture time. It
  holds:
  - the prepared case hash and the requested nice, with both of its sources;
  - the unit Nice and MainPID;
  - the observed NI per role;
  - the rank and processor-directory counts;
  - PID 1113 as Not recorded until it is enumerated;
  - the capture hash;
  - the deleted-executable fact.
- **The schema gains no field.** `cfd-case.schema.json:183-187` describes the prepared contract. An "actual" field would
  invite editing a case after launch.
- **Validity.** Nice changes only CPU scheduling. That a fixed 6-rank run gives identical numbers under different
  scheduling is Inferred, not measured. Cross-run timing comparisons must state the effective nice.
