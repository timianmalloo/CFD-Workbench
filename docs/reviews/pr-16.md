# PR #16 — Fable owner review

PR #16 "proof: report Ruling 163 Windows ring observations" (origin/win/r163-ring, reviewed head 60601554) was reviewed
by the Fable owner on the Mac on 2026-10-08 under Ruling 106. Verdict: **APPROVE WITH CONDITIONS**, issued as
**Ruling 167**. The Windows ring ceiling is ruled as **Ruling 168**.

## Findings

1. **Captures (Verified).** All 16 manifest entries match the committed blobs by SHA-256 and byte count, with CRLF
   kept. Source 77e53062 contains the CAF, RWF and PR #13 merges.
2. **Catalog passes on Windows (Verified).** The PASS lines are Core.part1of3.log:14-16, part2of3:13-15 and
   part3of3:13-15. The nine names are exactly the nine `Check("Catalog…")` calls at `CatalogTests.cs:17-25`. This is
   the first cross-OS confirmation of Ruling 156's deterministic generator. It is not yet P5, which needs a complete
   ring.
3. **DRIFT equals the Mac (Verified).** The lines are printed with `ToString("G17")`, so "0" is exactly zero. The
   6.1232339957367663E-18 is not a cross-OS difference. The Mac's own ring prints the identical line, and it equals the
   committed fixture value at `Fixtures/record-path/handle-target.tsv:7` (the 180° case, recorded before the SinCosPi
   switch). The code now yields 0 on both hosts (Inferred). All five Windows lines equal the Mac's.
4. **Claims (Verified).** "INCOMPLETE, not PASS, P5 unverified" is correct. The 60 s kill came from the Mac's own
   prompt to the PC; `tools/run-tests.sh` has a 60 s *budget*, which is advisory on Windows, and no kill.
5. **The C3 control (Verified).** `verify-captures.py` is sound, but it is local to this proof folder and runs in no
   gate. It proves this delivery. The class control is a Mac follow-up.
6. **Privacy (Verified).** 0 PROOF-PII hits. The PC audit entries carry no user path.
7. **Failures (Verified, with `check-expected-failures.py --host windows` on every captured log).**
   - Expected: Core 3+3+2, Desktop 2 and CLI 2, all manifest rows.
   - **Unexpected, and not listed in the receipt:**
     - (a) `Library_UserFileHeldReader_SurvivesReplaceByRename` threw `UnauthorizedAccessException`
       (Core.part2of3.log:91). This is the WSF behaviour test. The likely cause is test-side: it replaces the file with
       `File.Move(…, overwrite: true)`, which is not the product's POSIX handle-relative rename (Inferred; the Mac
       checks).
     - (b) `Section_WingRun_PanelValuesAtEveryStation` took 1145.9 ms against its 1 s limit (Mac: 391.6 ms). This
       repeats Ruling 154 (e), and its PC rerun-alone follow-up is still open.

  exists.
- The baseline is three rings **with L3 running**, at six-CPU affinity. L3 is not paused.
